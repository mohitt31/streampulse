# Interface decisions and proposed additions (no contract fields changed)

1. `forecast_refs` is interpreted as **zero-based indexes into parsed nonblank forecasts.jsonl records**. Blank lines are ignored. Producer and consumer must preserve record order. An optional future stable `forecast_id` would be safer than positional indexes.
2. `watch` is preserved exactly. The sample contract has a true watch even when the point prediction is below the reference; the intended decision rule is not supplied. The exporter does not invent one. Proposed optional addition: `watch_rule_id` plus parameters, threshold reference years and model-evaluation artifact identifier.
3. `generated_at` is exported as `Observation.issued`, following the agreed contract. This assumes generation is also publication to the prototype. If publication is delayed, propose a separate actual `published_at`. `issued_simulated` is exported only as the forecast-origin extension. Replay does not impersonate an actual historical issuance.
4. Source-calendar dates remain date precision. Forecast `effectivePeriod.start` and `.end` both equal `target_date`, meaning that single day at the available precision. This deliberately does not manufacture midnight UTC or turn an inclusive FHIR Period end into an extra calendar day. The original hourly source clock is preserved in the real-source example narrative/note; UTC/local timezone is UNVERIFIED.
5. Alert records supply no creation, publication, or delivery timestamp. Therefore the alert Communication has `status=preparation` and no `sent`/`received` timestamp. Application review state is stated separately. The completed acknowledgement Communication records the supplied `ack.at` as a demo acknowledgement event. It does not prove network delivery, authenticated identity, or completed sampling. Proposed optional additions: `created_at`, `sent_at`, `delivery_state`, authenticated actor reference.
6. `ack.at` must be an actual timezone-aware timestamp after real generation of all referenced forecasts. A simulated 2025 acknowledgement to a forecast generated in 2026 is rejected. If a UI replays historical acknowledgements, add an explicit simulated acknowledgement field; do not overload `ack.at`.
7. `weather_run_init` alone does not identify a provider, model, endpoint, URL, values, or retrieval snapshot. It is retained as supplied in forecast notes. The exporter does not fabricate weather provenance. Proposed additions: exact weather request URL, provider/model ID, retrieved_at, snapshot SHA-256, and input-manifest reference. Current Provenance references each supplied daily Observation and a clearly labelled upstream Hub'eau retrieval URL, not an independently verified pipeline download event.
8. The demo Organization is responsible for this representation/aggregation; it is not falsely labelled as the original sensor operator or an actual health authority. Model Device version is the supplied git SHA; SHA syntax is checked, existence and trained-model identity are UNVERIFIED. Propose a separate model-artifact digest.
9. The daily CSV has no station column. This exporter is intentionally single-station (05174000), as agreed; it rejects a different forecast station. Multi-site daily inputs require a future contract revision.
10. Fixtures use real measured/aggregated source values, but the forecast numbers, all-zero SHA, and acknowledgement are **synthetic** and explicitly labelled. No fitted-model forecast or skill metric was invented.
11. The component interval is accepted only when both bounds and point prediction are finite and ordered. Null intervals are outside the supplied contract and rejected; if the modelling pipeline intentionally omits uncertainty, revise the contract/profile explicitly rather than silently dropping required components.

## OAH derivation

No OAH constraint had to be weakened. The local forecast profile derives directly from the pinned OAH Indicator profile, keeps its final status, Location subject and required performer, and uses allowed Quantity/CodeableConcept values. Local prediction/metadata codes are explicitly defined under the user-authorized local canonical. Preferred OAH bindings allow these codes, with informational validator messages. These are experimental project definitions, not invented official profiles or terminology.

SUSHI must generate OAH snapshots (`--snapshot`) before the local IG can import the parent. A differential-only OAH build cannot be imported by SUSHI as a parent. The included build script implements this dependency order.
